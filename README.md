# Cadence

## Локальный запуск сайта

Требуется установленный Docker Desktop с Docker Compose.

1. Один раз скопируйте пример настроек:

```powershell
if (!(Test-Path .env)) { Copy-Item .env.example .env }
```

2. Запустите сервисы из корня репозитория:

```bash
docker compose up --build
```

При первом запуске Docker соберёт frontend и API, дождётся PostgreSQL и применит миграции.

- Сайт: http://localhost:5173
- API: http://localhost:5000
- Swagger: http://localhost:5000/swagger

Для остановки нажмите `Ctrl+C`, затем выполните `docker compose down`. Данные PostgreSQL сохраняются в volume. Чтобы удалить локальную базу вместе с данными, используйте `docker compose down -v`.

## Публичный запуск на VPS

Production-конфигурация запускает frontend, API и PostgreSQL в одной Docker-сети; снаружи доступны только HTTP/HTTPS через Caddy. Caddy автоматически запрашивает TLS-сертификат для домена. API и SignalR доступны с того же домена, поэтому браузер посетителя не пытается обращаться к его собственному `localhost`. База данных не публикует порт наружу.

1. Подготовьте Linux VPS с публичным IPv4-адресом. Направьте DNS-запись `A` вашего домена на этот адрес и разрешите во внешнем firewall входящие TCP-порты `80` и `443` (UDP `443` необязателен).
2. Перенесите на сервер файлы проекта из локальной ветки. Для этого можно использовать `scp` или архив; отправлять ветку в GitHub не обязательно.
3. В каталоге проекта на сервере создайте настройки и отредактируйте их:

```bash
cp production.env.example production.env
```

Укажите свой домен в `DOMAIN`, задайте уникальный длинный пароль PostgreSQL и случайный `JWT_KEY` не короче 32 байт. Не публикуйте файл `production.env` и не добавляйте его в Git.

На VPS можно получить два независимых секрета командами `openssl rand -hex 32`; один задайте как `POSTGRES_PASSWORD`, другой — как `JWT_KEY`.

4. Запустите production-сервисы из корня проекта:

```bash
docker compose --env-file production.env -f docker-compose.prod.yml up --build -d
```

После выдачи TLS-сертификата сайт будет доступен по `https://<ваш-домен>`. Посмотреть состояние и логи можно так:

```bash
docker compose --env-file production.env -f docker-compose.prod.yml ps
docker compose --env-file production.env -f docker-compose.prod.yml logs -f
```

Не запускайте локальный `docker-compose.yml` поверх production-конфигурации. Для реального сервера используйте только `docker-compose.prod.yml`; не открывайте порт PostgreSQL `5432` в firewall. Перед обновлениями сохраняйте резервную копию базы. Эта конфигурация использует один экземпляр API, поэтому SignalR-события между пользователями работают без дополнительной инфраструктуры. Если позже потребуется несколько экземпляров API, понадобится общий SignalR backplane, например Redis.

## Ручная проверка сценариев

1. Откройте сайт, выберите **Register**, создайте аккаунт с паролем не короче 8 символов и содержащим цифру. После регистрации сайт должен открыть список досок.
2. Создайте доску. Она должна открыться с колонками **To do**, **In progress** и **Done**. Обновите страницу и убедитесь, что доска по-прежнему открывается.
3. В другом окне браузера зарегистрируйте второй аккаунт. В первом окне на странице доски введите email второго аккаунта и нажмите **Invite**.
4. Во втором окне войдите под приглашённым аккаунтом и откройте эту доску из списка.
5. В первом окне создайте задачу, измените её, перетащите в другую колонку и удалите. Во втором окне каждое изменение должно появляться без ручной перезагрузки. Статус SignalR должен быть `connected`.
6. Обновите страницу обоих пользователей и убедитесь, что состояние совпадает с последним результатом на сервере.

## Автоматическая проверка API-сценариев

Для отдельного запуска тестов сначала подготовьте `.env`, поднимите PostgreSQL и затем запустите тесты:

```powershell
docker compose up -d postgres
```

Затем задайте строку подключения и запустите тесты:

```powershell
$env:TEST_CONNECTION_STRING = "Host=localhost;Port=5432;Database=cadence;Username=cadence;Password=change-this-local-password"
dotnet test Cadence.sln
```

Тест использует ту же локальную базу и автоматически применяет миграции. Для CI тесты выполняются на отдельном PostgreSQL service.
